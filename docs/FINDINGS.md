# Findings

Measured numbers only. Every number names the script that produced it;
result JSONs live under `bench/results/`. The public test corpus is
`tests/corpus/texts1000.json` (500 strings from the argmin learning
platform, CC-BY-4.0, plus 500 strings generated by
`tools/synthetic_texts.py`; built by `tools/build_corpus.py`).
Measurements below are on Playwright Chromium 151, Apple M1 Pro,
`limits: 'minimum'`.

## 1. Golden generation and tokenizer parity

`convert/golden.py`: per model, the 1,000 corpus texts with task `topic`
(10 demo labels), bucket L128/K16, under
`tests/golden/<model>/texts1000_l128k16.json`. Texts that overflow the
bucket are skipped and counted: small 968/1,000 used, base 968/1,000,
multi 953/1,000. Layer goldens: 8 texts in L128 and L256 under
`models/<model>/golden/` (not in git). Two-task cases: 20 texts with
`topic` + `sentiment`, softmax per task via `marker_groups`. Tokenizer
goldens: `tokenizer_ids.json` per model (1,000 texts each; Julia 1,330
texts).

`node --test tests/*.test.ts` (18 tests, all passing): 100 % equal
`input_ids` on `tokenizer_ids.json` (all 1,000 corpus texts per model,
plus the Julia set), 100 % equal `input_ids`, `marker_indices`,
`marker_mask` and `marker_groups` on `texts1000_l128k16.json` and
`two_tasks_l128k16.json`, for all three GLiNER models. Bucket overflow
throws `BucketOverflowError`. `tests/limits.test.ts` covers the minimum
limits including the wide L1280/K80 bucket.

## 9. Batch API (K16)

`classifyBatch` / `decideBatch` run up to 16 sequences in one GPU pass.
Parity (`bench/run-batch-parity.mjs`, minimum limits, mixed lengths):
batch outputs are bit-identical to single calls on B1/4/8/16, f32 and
f16, small-upstream and julia-1; argmax vs goldens 100 %.

A first throughput pass measured padded bucket rows per sequence (the
batch dispatched `bucket x B` rows while the single path dispatches
`seqLen`); batching did not pay off under that layout (e.g. julia B16
computed 49,152 rows for 7,693 needed). Batch plans now pack at a
64-quantized stride per chunk with inputs sorted by length.

Official throughput after the fix (ms per decision, ABAB, median of
3, start load < 6, same machine as section 8): small-upstream f16
L128 - B1 6.90, B4 6.39, B8 6.02, B16 8.83 (vs 6.8 single);
julia-1 f16 - B1 21.7, B4 35.8, B8 47.0, B16 46.2 (vs 24.9 single).

julia at B1 beating the single path is a measurement boundary, not
a GPU win: `bench/batch-bench.ts` times `runPreparedBatch` on
pre-tokenized inputs, while `decide()` on the single path includes
`prepareDecision` (BPE over state + question + options, ~3 ms per
request); GPU work is identical at B1 (same bucket plan, same
`submit(seqLen)` rows, `src/julia.ts`).

Dedicated head-to-head in one pass (ABAB, 3 reps, all official):
kh-julia-batch-f16-B1 20.3 ms/decision (20.35-20.45) vs upstream
batch-4 21.9 ms/request (21.89-21.99), argmax 100/100 both sides.
With equal boundaries (~3 ms tokenization) the batch B1 figure
would be ~23.3, still narrowly above upstream - both boundaries are
stated wherever the pair is cited. The B4-vs-B4 figures above
(35.8 vs 25.6) come from the throughput pass. Batching is kept for
the bit-identical parity and for hosts that batch anyway; single
calls remain the fast path for julia.

## 11. ONNX Runtime Web against the offline-fused graph (K20)

Question: does "kleinhirn is about 2.7x faster than ONNX Runtime Web"
hold against the best ORT graph we can produce?

### What the optimizer fuses

`convert/optimize_onnx.py`, results
`bench/results/k20-optimize-{small-upstream,julia-1}.json`.
onnxruntime 1.29.0 has no deberta or modernbert model type in
`onnxruntime.transformers.optimizer`; both models go through the
documented BERT path (`model_type bert`, default opt_level 1, 6 heads,
hidden 384). fp16 comes from the optimizer's own conversion of the
fused graph (`keep_io_types`). CPU parity is checked against the
PyTorch fp32 goldens (small: 968 corpus goldens; Julia: the 100 upstream
parity cases against our recomputed logits).

| Model | Nodes before -> after (f16) | Fused | Attention / MultiHeadAttention | File f32 / f16 (MB) | CPU parity f32 | CPU parity f16 |
|---|---|---|---|---|---|---|
| small-upstream | 1,571 -> 568 (571) | 24 SkipLayerNormalization, 12 Gelu, 1 LayerNormalization | 0 / 0 | 320.9 / 170.0 (plain 285.8 / 144.1) | argmax 100 %, max logit 2.4e-5 | 99.79 %, 0.066 |
| julia-1 | 1,353 -> 1,302 (1,303) | 22 Gelu, 1 BiasGelu | 0 / 0 | 577.0 / 288.6 (plain 579.8) | 100/100, 1.2e-4 | 100/100, 0.73 |

- The optimizer fuses the attention of neither model. DeBERTa-v2: the
  relative terms c2p and p2c match no attention pattern; 25
  GatherElements and 13 Softmax stay separate. ModernBERT: RoPE (Neg,
  Slice, Concat, Sin, Cos) and the windowed mask stay unfused,
  RotaryEmbedding 0.
- SkipLayerNormalization does not fuse for Julia. ModernBERT's
  LayerNorm has no bias; symbolic shape inference fails on the dynamo
  export, so the optimizer skips the fusion, and with shape inference
  disabled `fusion_skiplayernorm.py` stops with an IndexError.
- The fused small graph is larger than the plain export (320.9 vs
  285.8 MB) because opt_level 1 precomputes and stores the constant
  relative-position projections per layer.

Placement in the browser (`bench/run-ort-log.mjs`, ORT Web 1.29.0,
WebGPU, `log=verbose`, `bench/results/k20-placement-small-upstream-*.json`):
all four graphs place 10 nodes on `CPUExecutionProvider` (ORT puts
shape operators on the CPU on purpose) and the rest on WebGPU: f16
plain 837, f16 fused 588, f32 plain 690, f32 fused 585. The plain f16
graph carries 147 more nodes than f32, the cast pairs our fp16
conversion puts around the operators kept in f32. Fusion removes
them, which is why ORT gains most in f16.

A provisional screening pass (`--tag k20screen --reps 1`,
`bench/results/loadsens-k20screen-*.json`) chose the variants and
checked the Julia graph page: `bench/upstream-julia/bench-graph.html`
(the upstream benchmark loop verbatim, graph file and batch size as
parameters) measured 24.15 vs 24.16 ms per request against the
upstream page on the unchanged graph (batch 4), 29.03 vs 28.96
(batch 1). The Julia upstream pages run their own onnxruntime-web
1.30.0; the small ORT page runs our pinned 1.29.0.

### Graph capture

`enableGraphCapture` records the WebGPU commands on the first call and
replays them afterwards. ORT Web 1.29.0 passes the option to the WebGPU
EP only when the EP is given as an object (`{ name: 'webgpu' }`; with
the string `'webgpu'` the log reports `WebGPU EP graph capture enable:
0`). Inputs live in persistent GPU buffers (`Tensor.fromGpuBuffer`);
ORT allocates the outputs on the GPU itself, because output buffers
passed in beforehand fail on the second call (`Cannot set properties
of undefined (setting 'Symbol(gpuBufferMetadata)')`). Timed window:
from writing the inputs until the probabilities array lies in JS, one
readback; the logits for parity are read afterwards. `bench/ort.ts`
with `capture=1`.

- On the fused graph no session starts. All four graphs (f16/f32,
  plain/fused) fail with the same message: `This session cannot use
  the graph capture feature as requested by the user as all compute
  graph nodes have not been partitioned to the
  WebGpuExecutionProvider`
  (`bench/results/k20-placement-small-upstream-*-capture.json`). The
  cause is a MemcpyFromHost/MemcpyToHost pair around
  `/encoder/encoder/Squeeze` in the DeBERTa mask chain. ORT tolerates
  CPU nodes as long as no Memcpy is needed.
- `convert/capture_surgery.py` replaces `/encoder/encoder/Squeeze` and
  `/encoder/encoder/Unsqueeze_2` with one `Reshape` to the fixed shape
  [1,1,128,1] (element-identical, the input shapes are fixed). After
  that every node sits on WebGPU (f16 592, f32 589, CPU 0) and the
  session starts with capture. CPU parity is unchanged (f32 argmax
  100 %, max logit 2.4e-5; f16 99.79 %, 0.066;
  `bench/results/k20gc-surgery-small-upstream.json`). After the first
  call `run` returns in 0.3 to 1.0 ms instead of 16 to 20 ms; the GPU
  work runs in the replay.

Official pass, same rule as above, commit 2b7dacd, prefix
`k20gc-official`. The f32 pair kleinhirn vs capture was rerun as

### Findings

- "About 2.7x faster than ONNX Runtime Web" does not hold. Against the
  best ORT configuration we could produce (fused graph, rewrite for
  capture, graph capture) kleinhirn is 1.9x faster in f16 and 2.2x in
  f32, and 2.6x on the WASM path, which has no capture. Without
  capture it was 2.2x and 2.7x: the optimizer gains 18 % in f16
  because it removes the casts of our fp16 conversion, capture another
  15 to 16 %.
- Both ORT fp16 graphs miss our fp16 probability gate (at most 1e-2):
  plain 5.3e-2, fused 3.5e-2. kleinhirn f16 is at 4.2e-3. All three
  pass the argmax gate (at least 99.5 %).
- Julia: against the fused fp16 graph the upstream loop is faster than
  kleinhirn, by 1.12x at equal boundaries and 1.31x between the
  fastest paths, although kleinhirn's batch number excludes
  tokenization. That graph deviates up to 1.02 in logits from PyTorch
  fp32, kleinhirn f16 by 0.091. In f32 the two are level.
- Memory: kleinhirn peaks at 45 to 63 % of the fused ORT path in every
  pair (small f16 59 %, f32 50 %, WASM 45 %, julia f16 62 to 63 %; against
  ORT with capture f16 58 %, f32 49 %, provisional); no ranges overlap. Download: small f16 152.3 vs 187.7 MiB. For Julia
  f16 no download advantage is measured; the upstream page was not
  measured.
- Graph capture: the earlier assumption that the 10 CPU nodes block
  it was wrong; two Memcpy nodes did, and capture runs after the
  rewrite (above). Not tested for Julia.

## 12. Where the GPU time goes (per-dispatch profile)

Question: which kernel costs the time, and is it spent on the GPU or on
dispatch and CPU work?

`bench/run-profile.mjs <model> <precision>` runs the profiling mode
`profile(input, { granularity: 'dispatch' })`: every dispatch gets its
own compute pass with timestamps, with the same pipelines, bind groups,
dispatch sizes and order as the normal path, at the item's real
sequence length. 20 warm-up profiles, then 200 items (small-upstream:
the first 200 L128 goldens, sequence length 29 to 120, median 50.5;
julia-1: the 100 parity requests twice, 22 to 258, median 65.5). Per op
the median over items of the sum over all layers; wall time from the
normal path on the same page. Commit 9f67fd8, Chromium 151.0.7922.34,
start load 3.42 to 3.95. The profiled forward's logits are
bit-identical to the normal path for 20 of 20 items. Files
`bench/results/k27-profile-{small-upstream,julia-1}-{f16,f32}.json`.

Without a flag Chromium quantizes timestamps to a 65.5 µs grid (17 to 43
distinct values per run), so the profiles run with
`--enable-webgpu-developer-features`: 3,280 to 8,774 distinct values,
smallest step about 3.5 µs.

| Profile | GPU sum per forward, median ms | Wall time ms | Encoder matmuls | Encoder attention | Head | Other ops |
|---|---|---|---|---|---|---|
| small-upstream f16 | 6.79 | 7.2 | 65 % | 30 % | 1.5 % | 4 % |
| small-upstream f32 | 7.16 | 7.5 | 65 % | 29 % | 1.7 % | 4 % |
| julia-1 f16 | 19.93 | 21.25 | 59 % | 26 % | 8 % | 7 % |
| julia-1 f32 | 22.29 | 24.35 | 58 % | 25 % | 8 % | 9 % |

Shares of the sum of the per-op medians. Encoder matmuls: qkv, attnOut
and the two FFN projections; head: the GLiNER head, or Julia's two head
layers plus scorer; other ops: embedding, LayerNorm, RoPE, add, GeGLU.
The FFN projections alone take 42 % (small f16) and 40 % (Julia f16).

Findings:
- The time is spent on the GPU: wall time minus GPU sum is 0.3 to 0.4 ms
  for small-upstream and 1.3 to 2.1 ms for Julia, upload and readback
  included. Graph capture of the kind ORT uses would gain kleinhirn
  little.
- The encoder matmuls take 58 to 65 % of GPU time, and all of them run
  through one kernel (`src/kernels/matmul.wgsl`). A kernel search starts
  there; attention (25 to 30 %) comes next.
- Julia's attention grows with length: the p95 of its attention sum is
  20.3 ms (f16) against a median of 5.0 ms.
- After the profiling refactor the normal path still matches the
  PyTorch goldens to the third digit, for small-upstream and julia-1 in
  f32 and f16, plus batch B4 in f16
  (`bench/results/2026-09-29-parity-*.json`).

### Findings

- Parity holds on every stage that runs, on every desktop browser we
  have. Latency misses the L256 target everywhere: Chromium f16 at 46.7
  ms against 20 and WASM at 453.3 ms against 300. The desktop gap in
  Chromium is more than a factor of two; the kernel search has to close
  it. The dispatch profile of section 12 covers L128 only.
- The 80 MB download target is missed by f16 at 152.3 MiB. Vocabulary
  compression and int8 weights are the way down.
- wasm runs on the iPhone with exact parity (one WebDriver run) but needs 615 ms end-to-end median in L256, 3.5 to 4.2 times f16 (145 and 176 ms in the two WebDriver runs). The page picks f16 on the iPhone whenever WebGPU is there; wasm stays the path without WebGPU.
- f16 stays the mobile path: the page picks it on the iPhone by itself,
  parity holds, and f32 is no faster there. The iPhone 16 Pro is about
  four times slower than Chromium on the M1 Pro in L128 f16 and misses
  the L256 target by about 2.8 times. The kernel search has to close
  that gap; whether 60 ms is reachable in L256 needs an L256 dispatch
  profile first.

## 15. Kernel rewrite after looking inside ORT (K27)

Question: why was ORT faster at full length, and can kleinhirn catch up
without leaving its rules (WebGPU minimum limits, no subgroups, f32
accumulation, parity)?

Diagnosis (`bench/k28-ort-trace.html` records every WGSL shader ORT
creates and its dispatches; `bench/k28-kh-profile.html` times
kleinhirn per dispatch): ORT requests more than the minimum limits
(1,024 invocations, 32 KiB workgroup memory) and the `subgroups`
feature, but its MatMul calls no subgroup function. Its MatMul has every
thread compute a 4x4 block from vec4 tiles of 2 KiB, which fits the
minimum limits, and accumulates in f16. kleinhirn's matmul computed one
output per thread (78 % of the GPU time of RoBERTa at L128), and its
attention re-read all keys and values for every query row.

Changes (`src/kernels/`):
- Register-blocked matmul in three tile sizes (32x64, 16x32, 8x32), each
  thread a block of 4, 2 or 1 rows by 4 columns, vec4 tiles in the
  storage type, f32 accumulation in the same k order as before. All three give the same
  bits as the old kernel; each call takes the largest tile that still
  starts enough workgroups for its row count.
- Attention as three matmul-shaped kernels: scores, softmax and context
  (f32 scores and probabilities). DeBERTa's relative terms are matmuls
  over the relative positions the bucket can reach. Tiles outside the
  valid tokens of a sequence are skipped (first and last valid token per
  sequence, written at upload).
- Rejected after measurement: split-K, weights stored transposed, 64x64
  tiles, and one thread per query row for attention (too few threads at
  128 tokens).

Checks: twelve canary models in f32 and f16 keep the decisions of the
gate in section 14; GLiNER2.5-small, Julia 1 and the batch path keep
their gates; the kernel choice by row count does not change a single
output bit. Playwright WebKit and Firefox give the same decisions as
Chromium on four families.
