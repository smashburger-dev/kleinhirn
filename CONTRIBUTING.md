# Contributing to kleinhirn

Thanks for your interest. Help is welcome, and most of it does not need
code: a result from your device, a bug report with the browser and GPU,
or a model that gives a different answer than PyTorch are all worth as
much as a pull request.

## The easiest way: a device result

Open the device benchmark page at
https://smashburger-dev.github.io/kleinhirn/, let it run, download the
result file and open an issue with the
["Device result" form](https://github.com/smashburger-dev/kleinhirn/issues/new?template=device-result.yml).
A maintainer checks parity by script and adds the result to
[`docs/COMMUNITY.md`](docs/COMMUNITY.md). What the file contains is
described in [`docs/device-results.md`](docs/device-results.md); read it
before you post it.

## Reporting a bug

[Open an issue](https://github.com/smashburger-dev/kleinhirn/issues/new/choose)
and say what you ran, what you expected and what happened. Name the
browser and version, the OS, the GPU (or "no WebGPU"), the model and the
backend (`auto`, `webgpu`, `wasm`). A wrong answer is a bug too: name the
input text and the answer of the PyTorch reference.

Security problems do not go into a public issue; see
[`SECURITY.md`](SECURITY.md).

## Before you write code: open an issue first

For anything larger than a typo or a one-line fix, open an issue and
describe what you want to change and why, before you write the code. A
maintainer answers whether it fits the project. This saves you work on a
change that cannot be merged, for example because it adds a runtime
dependency or changes a measured number without a measurement.

## Setting up

You need [Node.js](https://nodejs.org/) 24 or newer (the tests use
`Float16Array`) and, for conversion and goldens, Python 3.12.

```bash
npm ci
npm run typecheck
npm test
```

Model weights are not in git. Tests that need a model are skipped when
`models/` does not have it. How to fetch and convert models is in the
[README](README.md) under the build and test section.

## What makes kleinhirn kleinhirn

- **Same answers as the reference.** The reference is PyTorch in f32.
  A change that touches kernels, the graph, the tokenizer or the weight
  format must keep parity against the goldens, and the pull request says
  how that was checked.
- **Numbers are measured, not claimed.** A change that claims a speed-up
  comes with the measurement: the model, the bucket, the device and
  browser, repetitions, and the command. The protocols are in
  [`docs/BENCHMARKS.md`](docs/BENCHMARKS.md) and
  [`docs/FINDINGS.md`](docs/FINDINGS.md).
- **No server, no runtime dependency.** The engine needs WebGPU or its
  own WASM module, nothing else. onnxruntime-web is only the measurement
  baseline in `bench/`. New packages in `dependencies` are not accepted.
- **The engine computes; it decides nothing.** Thresholds, abstention and
  texts belong to the application.
- **Small and readable.** A small, clear change is better than a large
  rewrite. The design is in [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md).

## Pull requests

- **One topic per pull request.** A bug fix, a kernel change and a
  README edit are three pull requests.
- **Keep it small.** Pull requests from people without write access are
  closed automatically when they change more than 800 lines or more
  than 20 files. If a larger change is really needed, agree on it in an
  issue first; a maintainer can then let it through.
- **Link the issue** the pull request belongs to (`Fixes #123`).
- **Say what you checked.** The template asks for it: typecheck, tests,
  parity, and measurements where they apply.
- **Do not touch generated or pinned files by hand.** Goldens, converted
  weights, `src/wasm/deberta.wasm` and `pages/` are generated by the
  tools in this repository; pinned revisions and hashes change only with
  a reason.
- **Changes to `.github/workflows/`** from outside contributors are only
  accepted after discussion in an issue.

### Code written with AI tools

That is fine, under the same rules as any other code: you have read and
understood every line, you have run the checks yourself, and you can
answer questions about it in the review. Say in the pull request that a
tool was used. Pull requests that are clearly generated and not checked
(invented APIs, claims without measurements, unrelated reformatting) are
closed without a detailed review.

## Style

- English for code, comments, docs and commit messages.
- Plain sentences in docs; numbers with their unit and their source.
- Commit messages say what changed and where, for example
  `Tokenizer: XLM-R handles empty input`.
